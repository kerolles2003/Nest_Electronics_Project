## 3. NestJS version selection

### The blocker

`@nestjs/cli@12` declares a **direct dependency** `typescript: ~6.0.2`, and `@nestjs/schematics@12` declares `peerDependencies.typescript: ">=6.0.0"`.

The workspace is on TypeScript **5.9.3**, and this phase is explicitly forbidden from upgrading TypeScript.

> **Adopting NestJS 12 requires a workspace-wide TypeScript major upgrade (5 → 6). That is a proven hard compatibility blocker, and this phase does not perform it.**

### The selection

**NestJS 11.2.3.**

| Evidence | Value |
|---|---|
| `@nestjs/schematics@11` peer | `typescript: ">=4.8.2"` → **5.9.3 satisfies it** |
| `@nestjs/cli@11.0.24` bundled TypeScript | **`5.9.3`** — byte-identical to the workspace version |
| `@nestjs/core@11.2.3` engines | `node >= 20` → 24.11.0 satisfies |
| `@nestjs/platform-express@11.2.3` | `express 5.2.1` → typings must be `@types/express@^5` |

This is not an outdated tutorial version: 11.2.3 is the current head of the actively-maintained Nest 11 line, and its official CLI ships the *exact* TypeScript the workspace already has. The fit is exact rather than merely tolerable.

**Upgrade path, for a future phase:** upgrade TypeScript workspace-wide to 6.x, then move the Nest packages to 12.x together. Both halves must move at once; neither is a Phase 2.2 decision.

**Nothing else was upgraded.** Next.js, React, TypeScript, pnpm and Turborepo are untouched (§4.2 shows this was verified, not assumed).

### 4.2 The exact pin on `typescript-eslint` — and why

First install used `typescript-eslint@^8.68.0` (then-latest). Diffing the lock file afterwards showed **unintended collateral**: pnpm deduplicated `@typescript-eslint/*` across the workspace, moving `apps/admin`, `apps/storefront` and `packages/ui` from `8.59.1` → `8.68.0` — an upgrade of tooling in applications this phase must not touch.

The lock file was **restored from the pre-install copy**, the dependency pinned to `8.59.1` (the version `eslint-config-next@16.2.4` already resolves to), and the install re-run.

**Result: `apps/admin`, `apps/storefront` and `packages/ui` importer blocks are byte-identical to before.** Verified programmatically; zero occurrences of `8.68.0` remain in the lock file.

> An exact pin rather than a range is deliberate: any caret range would re-resolve to the newest 8.x and reintroduce the dedup shift. The pin is a *containment* decision, documented here so it is not mistaken for carelessness.

### 6.1 Global HTTP foundation

| Mechanism | Registration | Frozen authority |
|---|---|---|
| Global prefix `api` + URI versioning `v1` | `main.ts` | `API-CONTRACT.md` §1 |
| Helmet security headers | `main.ts` | `API-STANDARDS.md` §6 |
| Swagger / OpenAPI | `main.ts`, non-production | `API-CONTRACT.md` §8 |
| Shutdown hooks | `main.ts` | brief §Shutdown |
| `RequestIdInterceptor` | `APP_INTERCEPTOR` | `CROSS-CUTTING-STANDARDS.md` §C1, §C2 |
| `AllExceptionsFilter` | `APP_FILTER` | §C1, §B1 |
| `ValidationPipe` | `APP_PIPE` | §C1, `API-STANDARDS.md` §4 |

**Why `ValidationPipe` is registered before any DTO exists.** `forbidNonWhitelisted` is a security control — the thing that makes `role`, `stock`, `userId` and `price` injection structurally impossible. Its value comes from being in place *before* the first DTO is written; added afterwards, it is the classic control everyone forgets. `API-STANDARDS.md` §4 calls the configuration "non-negotiable", and the brief permits establishing global validation infrastructure where the frozen architecture requires it.

**Why the request-id logic is a shared function, not duplicated.** An unmatched route never reaches an interceptor — Nest's router throws before any handler runs — so the filter cannot rely on the interceptor having run. Both call the same idempotent `resolveRequestId(request)`, which memoises on the request object. This is why a 404 still carries a correlation id (verified in §8).

### 6.2 Health

Liveness only, and **deliberately dependency-free** — it proves the HTTP runtime is answering, nothing more. It requires no authentication and discloses no version or internal hostname, per `API-STANDARDS.md` §10.

## 8. Documentation ambiguity recorded (not resolved)

> **`API-CONTRACT.md` §3 states "One envelope, always" — `{ data, … }`. `API-STANDARDS.md` §10 documents health as returning a bare `{ status: "ok" }`, with no envelope.**

Both are frozen. They disagree about whether the health endpoints are exempt from the response envelope.

**Phase 2.2 implemented `API-STANDARDS.md` §10 verbatim** (bare `{ status: "ok" }`), because it is the more specific statement about this endpoint and matches what orchestrators and load-balancer probes expect. Since `TransformInterceptor` is deferred, no behaviour depends on the resolution yet.

**This is recorded, not resolved.** It must be settled before the envelope interceptor is introduced, since that is the phase where the two documents produce different code. Consistent with the ratification-era instruction: *identify the conflict explicitly; do not silently choose one interpretation.*

A second, minor gap: the frozen documents show `requestId` values in ULID form (`01JC8XQZ…`) in examples but never specify a format normatively. This phase uses `crypto.randomUUID()` — zero dependencies. If ULID is intended, that is a one-line change plus a dependency, and should be decided alongside structured logging.

### 9.1 Two defects found by verification and fixed

Both were introduced by this phase and caught by executing the runtime rather than trusting the code.

| # | Defect | Cause | Fix |
|---|---|---|---|
| 1 | `X-Frame-Options: SAMEORIGIN` and `Referrer-Policy: no-referrer` | Helmet 8 defaults differ from the frozen table, which requires `DENY` and `strict-origin-when-cross-origin` | Explicit `frameguard`, `referrerPolicy` and `strictTransportSecurity` options |
| 2 | **A second build emitted only `main.js`; a third emitted nothing** | `"incremental": true` in `tsconfig.json` conflicts with `nest-cli.json`'s `deleteOutDir: true` — a stale `.tsbuildinfo` told tsc the output was current while Nest had just deleted `dist/` | Removed `incremental`. Builds verified repeatable. |

> Defect 2 is the reason this plan insists on running the artifact rather than reading it. The first build succeeded and the API ran correctly; only the *second* build exposed a broken toolchain that would have failed in CI on the next commit.
